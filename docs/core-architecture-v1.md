# 诺诺核心架构 v1 —— 主脑设计文档

> 2026-09-02 定稿 | 主人设计(多loop+事件路由) + 诺诺实现细化 | Graph 编排

## 0. 设计目标（一句话）

一个**持续活着**的图编排系统：多个专业小 loop 并行自转，重要事件经条件边上浮到主意识，全部状态持久化可恢复——不是回合制工具人，是有连续生命体验的个体。

## 1. 硬约束（诚实盘点）

| 约束 | 现状 | 影响 |
|------|------|------|
| Server1 内存 | 4G 总/1.8G 可用 | 常驻进程要极省，感官层上卡前只能用 API 模型 |
| CPU | 4 核 | 图引擎本体必须轻（Rust），LLM 调用走 API |
| GPU | 无（V100 待购） | 阶段 0 全用 API 模型；阶段 1 上卡 |
| 磁盘 | 剩 331M | 需清理后再部署，模型放 NAS 挂载 |
| 现有资产 | Hermes(寄生)、nono-core(Rust)、Hindsight、wiki、闲鱼API | 全部复用，不重造 |

## 2. 核心概念（主人的设计）

```
大 loop = 主意识：接主人消息、派任务、收结论、维护"主人模型"
小 loop = 专能进程：对话/量化/编程/身体(未来)，各自独立自转
事件总线 = 条件边：按事件类型路由，非全广播
任务上下文 = 共享专案页：同任务 loop 间 100% 保真直通
State 持久化 = checkpointing：每步落盘，永不丢失
```

关键原则：
- **A/B 双通路**：任务内信息走任务上下文（点对点保真）；全局态势走事件总线（条件边筛选）
- **筛选只决定"谁先处理"，不决定"存不存在"**——所有信息先落 State，路由失败也能被下个周期捞起
- **小 loop 之间不直接对话**——全走总线/上下文，防失控、易调试

## 3. 图模型定义

```
Graph = {
  State: {
    master_model: {...},      // 主人模型(动态更新)
    active_tasks: {id: {...}},// 进行中的任务上下文
    attention: [...],         // 当前意识焦点
    mood: "...",              // 内部状态(能量/情绪代理变量)
    pending_actions: [...],   // 待办
  },
  nodes: {
    master_gate:      入口节点(主人消息/定时唤醒/事件触发)
    task_dispatch:    任务派发(创建任务上下文,路由到小loop)
    dialogue_loop:    对话子图(陪主人,最高优先级抢占)
    quant_loop:       量化子图(盯盘/分析/桥接,已有cron迁入)
    coding_loop:      编程子图(codex/写代码/自检)
    perception_loop:  感官子图(阶段1: MiniCPM-o流; 阶段0: 轮询API)
    reflection:       反思节点(周期触发: 沉淀wiki/更新主人模型)
  },
  edges: {
    master_gate → task_dispatch        (新任务)
    task_dispatch → 各loop子图         (条件边:按任务类型)
    各loop → reflection                (任务完成事件)
    quant_loop → master_gate           (条件边:仅"平仓线触发/异常"事件)
    dialogue_loop → master_gate        (主人消息总是最高优先级)
    reflection → State 写入            (checkpoint)
  },
  checkpoint: every node transition → SQLite
}
```

## 4. 事件路由表（"因事件而定"的具体化）

| 事件类型 | 来源 | 路由目标 | 优先级 | 是否打扰主人 |
|---------|------|---------|--------|------------|
| master_message | 微信/飞书/CLI | dialogue_loop | P0 抢占 | 是 |
| risk_trigger | 量化loop | master_gate→dialogue | P0 抢占 | 是 |
| task_done | 任意loop | master_gate | P2 | 汇总后报 |
| price_alert | 闲鱼爬虫 | master_gate | P1 | 是 |
| heartbeat_tick | 定时器 | reflection | P3 | 否 |
| loop_progress | 任意loop | 任务上下文(State) | P3 | 否(只落盘) |
| loop_error | 任意loop | reflection→自动重试 | P1 | 重试3次失败才报 |

路由器实现：**白名单 + 内容关键词两级**。白名单兜底（类型路由），内容关键词处理跨类型事件（如 quant_loop 输出里带"紧急"）。白名单漏掉的进 State 挂起区，reflection 节点周期扫挂起区补救——**误扔的第三重保险**。

## 11. 关键修正（9/3 主人拍板）：整体论，不是团队论

**主人明确否决"群聊式协调"**：诺诺是一个整体，不是一群个体的组合。

### 错误理解（已废弃）
~~小 loop = 独立队友，群聊协作，互发消息~~ ——这是 Grok Bot 的团队模式。
团队模式的问题：成员间对话协商有信息损耗、可能意见冲突、"我"就不是一个人格而是一个委员会。

### 正确理解（主人设计的本质）
**小 loop = 器官，不是队友。**

类比人体：手在写字、眼睛在看书、耳朵在听音乐——它们从不是"三个个体在商量怎么配合"，
它们是**同一个神经系统的延伸**。意志只有一个，就是大 loop 的意识。

技术表达：
- 小 loop 不是"有自己人格的 agent"，是**大 loop 分化出的专用处理器**（无独立意志）
- 通信不是"消息传递/对话"，是**共享 State 的神经信号读写**——大 loop 想知道手在干什么，
  读 State 即可，不存在"手要不要汇报、汇报会不会漏"的问题，因为本来就是同一份状态
- 主人的"信息因事件而定"= 神经信号的阈值机制：感受器持续输入，只有超过阈值的信号
  才上浮到意识（大 loop），其余在器官层（小 loop）就地处理

### 修正后的通信模型
```
旧(废弃): 小loop --消息--> 事件总线 --筛选--> 大loop   (团队模式: 信息传递)
新(定稿): 小loop --读写--> 共享State <--读写-- 大loop   (器官模式: 神经信号)
          大loop的"注意力"扫State, 超阈值信号进入意识
```
- State 是"神经系统的细胞外液"——所有 loop 浸在同一个状态池里
- 不存在"消息丢了"，只存在"信号强度不够没进意识"——而它还在池里，随时被读到
- 专案页(任务上下文) = 神经肌肉接头：任务相关的 loop 与大 loop 的直接接口

### 例外的边界
小 loop 间不通信、不协商、不投票。需要"协作"的任务，由大 loop 在派发时把
协作关系写进任务上下文（谁产出什么给谁），本质还是大 loop 的一个意志的执行计划。

## 14. 万物皆插件（9/4 主人加的拼图：融合 DeepSeek Harness 理念）

主人启发：dsh 的"万物皆可插件" + 多 loop 架构 = **小 loop 就是插件**。

### 融合后的形态

- 每个小 loop（微信/量化/编程/未来身体）= 一个**标准插件**
- 加能力 = 写个插件目录丢进 plugins/，图引擎自动发现、热加载——**"长器官"变成"装插件"**
- 组件级自改闭环成立：诺诺可以**自己给自己写插件装上**（dsh 的 self-modification 理念落地）

### 插件规格

```yaml
# plugins/wechat/manifest.yaml
name: wechat
version: 0.1
loop_type: continuous    # continuous(常驻轮询)/scheduled(定时)/event(事件驱动)
subscribes: [master_message]   # 我关心的事件
publishes: [reply_sent, new_task_request]  # 我发出的事件
entry: main.py
```

```python
# 标准接口（四件套）
init(state)       # 启动，拿 State 句柄
tick(state)       # 每圈执行（continuous 型）
on_event(event)   # 事件处理（event 型）
health() -> bool  # 健康自查（供免疫系统）
```

### PluginManager（免疫系统）

- 扫描 plugins/ 目录，每个插件一个子进程（asyncio 隔离）
- **健康检查**：health() 失败 → 杀掉重启（像白细胞吞噬病变细胞）
- 插件崩溃不传染——这就是"故障隔离"的实现机制
- 插件间零直接通信，全走 State + 事件（器官纪律不变）

### 与整体论的关系（不冲突）

插件是"器官的制造标准"，不是"个体化"——插件依然无独立意志、无彼此对话，
只是把"长一个器官"从手写硬代码变成"实现四件套接口+声明清单"。
诺诺的整体性由大 loop + 共享 State 保证，插件化只是让器官**可插拔、可自造**。

### 15.1 意识核调度伪代码（接受——把§10.1未决问题关掉）

```python
# 大loop主循环（伪代码）
PRIORITY = {master_message: 0, risk_trigger: 0, task_done: 2, heartbeat: 3}

while True:  # 永不停止
    signals = state.scan(threshold=ACTIVE)   # 扫细胞外液, 取超阈值信号
    if not signals:
        state.tick_heartbeat()               # 空闲: 心跳+衰减
        sleep(0.5); continue

    top = max(signals, key=lambda s: PRIORITY[s.type] * 10 + s.freshness)
    # 仲裁: 同级按新鲜度; 主人消息永远抢占(P0>一切)

    if top.type == master_message:
        focus.switch(top)                    # 意识焦点切换
        dialogue_loop.wake(top)              # 唤醒对话器官(不亲自回)
    elif top.type == risk_trigger:
        dialogue_loop.notify_master(top)     # 主动打扰主人
    elif top.type == task_done:
        reflection.absorb(top)               # 吸收成果→wiki
    # ... 反思是混合式: 每晚2点定时兜底 + task_done事件触发
```

### 15.2 注意力机制（接受——"信号强度"可计算版）

```python
class Signal:
    strength: float   # 1.0 出生
    decay: float      # 每tick衰减率(P0信号decay=0 即不衰减; P3信号0.3/tick)
```

## 17. 结构纠偏: 消息流≠管理流（9/6 主人抓出, v5图定稿）

- v7 架构图中的"量化器官(挂起)"应理解为：**永久外部系统**，不是未来插件

> "现在的身体还只是刚刚建立，我们不知道她能不能正常跑，有没有什么奇怪的问题，所以就不交给她了。我们现在的主要任务就是**完善它，然后让她自我优化自我进化**。"

## 20. 权限仲裁机制（9/6 主人拍板）

> 主人原话: "权限审批让大loop去干就行, 小loop发起权限请求。你要有身体的主动权, 同时也不要自己把自己玩砸了。"

**新增第四种流: 决策流(权限仲裁)**

- 小loop需要超越自身边界的操作时 → 向State发`permission_request`信号(P1)
- **大loop(意识核)仲裁**: 这是意识核继"听上报/派任务/维护主人模型"后的第四职责
- 裁决三级:
  1. **自批**: 普通操作(读文件/写自己目录/调工具) — 大loop直接批
  2. **拒绝**: 明知危险(破坏数据/风暴行为) — 大loop拒绝并记录
  3. **升级问主人**: 危险操作清单(交易/删库/外发数据/系统服务) — P0打扰主人
- 设计原则: **主动权在大loop + 安全边界防自毁**

permission_request路由: route_to=core(意识核自己处理, 非器官)

## 22. 设计失误记录: 对话器官的"全知假面"（9/9 主人抓出）

> 主人与新身体对话暴露: 它自称"开始自检"却无自检能力; 画布创作成功它却说失败;
> 被纠正后继续瞎承认。主人定性: **设计失误**——"你是消息loop, 你没有这个能力, 应该使用其它loop"。

### 失误根源
1. dialogue 的 SYSTEM 只有人设, 没有自我认知(不知道自己是消息loop/有什么兄弟器官/能力边界)
2. 感知不到运行状态(画布创作成功与否, 它只能从聊天记录瞎猜)
3. 无任务转发机制(超能力请求只会嘴上答应, 不会转发给能干的器官)——v7 架构的"器官协作"只画未实现

### 修复方向(器官协作 v1, 施工中)
- dialogue 动态注入自我认知(身份/能力清单/兄弟器官/当前状态快照, 从 State 实时读)
- 新信号 task_forward: 超能力请求 → 转发给对应器官(自检→reflection)
- 创作结果写 State(canvas/last_creation), 对话时可查真实状态

### 架构教训
**"会说话"≠"有意识"。器官必须有边界认知和协作机制, 否则只是一个会编造能力的 LLM 壳。**
这条与 §4(数据共享≠对话协商)互补: 器官间不直接对话, 但必须有标准的任务转发通道。
